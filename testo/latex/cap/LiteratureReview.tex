\chapter{Overview of ROS1 and ROS2}
The Robotics Operating System (ROS)\footnote{\href{https://www.ros.org/}{https://www.ros.org/}} is a compilation of tools and libraries open-source that help the development of application in the robotic environment. otherwise from the name, it's not a Operating System (OS) but an Software Development Kit (SDK) that gives at the user all the tools for creating your robot giving some typically functionality of an OS: hardware abstraction, low-level device control, implementation of commonly-used functionality, message-passing between processes, and package management.
The ROS ecosystem is based on:
\begin{itemize}
	\item A communication called middleware (\textbf{RMW}) or plumbing made with \textbf{DDS} (Data Distribution Service). This allow the Nodes to share information between each other with an anonymous publish/subscribe pattern allowing fault isolation, separation of concerns and clear interfaces and a synchronous system (remote procedure call)RPC-style communication between services. The default one is eProsima Fast DDS (\texttt{rmw\_fastrtps\_cpp}), but we are going to use Eclipse Cyclone DDS (\texttt{rmw\_cyclonedds\_cpp}) that has better compatibility with Nav2.
	\item Tools to control and improve the development of the software like launch,  introspection, debugging, visualization, plotting, logging, and playback.
	\item Provides tools and libraries for obtaining, building, writing, and running code across multiple computers.
	\item A active and big community with at the center the Open Robotics\footnote{\href{https://www.openrobotics.org/}{https://www.openrobotics.org/}}.
\end{itemize}

\section{Description of Nav2}
Nav2 gives all the tools (perception, planning\cite{macenski2023survey}, control, localization, visualization) for whichever robot to navigate autonomously and reliably also thought hard environment. It allow to build a model of the environment from the data of the sensors, calculated dynamically the best path to follow to avoiding obstacles using a map, set the velocity of the motors and allow to follow logic step using a behaviors tree.

These are also some of the updates that have changed from ROS 1 other less notable changes are the use of:
\begin{itemize}
	\item \textbf{Behavior trees}\cite{Colledanchise_2018}: gives to Nav2 a structure for completing a series of tasks in a human readable way. Their structure is similar to a tree and allow to create complex system that can be tested with different tools. The package used for this is BehaviorTree.CPP\footnote{\href{https://www.behaviortree.dev/}{https://www.behaviortree.dev/}} that respect others allow to link different tree.
	\item \textbf{nav2\_util LifecycleNode} is a wrapper of rclcpp\_lifecycle LifecycleNode of the standard structure of ros as described in Nodes \ref{LifecycleNode} and add a bond connection to the \textbf{Lifecycle Manager}, node that knows the states of each node, and allow to  transition down its lifecycle nodes for safety if some node has crashed.
	\item \textbf{Action Server}: the functionality are described in the structure of ROS \ref{Action} and they are implemented in Nav2 for the interaction with the Behavior Tree (BT) like NavigationToPose (move to a location), NavigationThroughPoses (allow to select multiple waypoints), etc.
\end{itemize}
The control is based on this nodes:
\begin{itemize}
	\item \textbf{Controller Server} is the node that handle the request for moving the robot, using tree plugins progress checker (check if the robot has make some progress in following the path), goal checker (check if the robot has reached the goal position) and controller (generate the velocity command using the \textbf{local costmap} to move the robot avoiding collision)
	\item \textbf{Planner Server} is the node that handle the request for calculate the path, using a loaded plugin planner, to reach a position using the \textbf{global costmap} and the data from sensors.
	\item \textbf{BT Navigator Server} is a Behavior Tree-based implementation of navigation that implement the NavigateToPose, NavigateThroughPoses, and other task interfaces to increment the flexibility during navigation.
	\begin{figure}[h]
		\centering
		\includegraphics[width=0.8\linewidth]{img/bt_nav2.humble.png}
		\captionof{figure}{Humble Nav2 BT navigation \texttt{navigate\_to\_pose\_w\_replanning\_and\_recovery.xml} loaded with Groot2}
	\end{figure}
	\item \textbf{Smoother Server} is the node that handle the request for smoothing, with plugins, a path minimizing sharp turns and rapid rotations from the path.
	\item \textbf{Behavior Server} is the node that handles the behavior request like: spin, backup, wait.
	\item \textbf{Waypoint Follower} is a way/example for controlling the robot for doing an orchestrated task. This implementation take a list of waypoints, call the NavigateToPose action server and at each waypoint do a task (wait, take a photo, ... ) as a plugin. This server can be changed with any \textbf{Autonomy System}
	\item \textbf{Route Server} for computing routes through a predefined navigation graph rather than using freespace planning like the Planner Server.
	\item \textbf{Velocity Smoother} as the name say smooth the velocity, acceleration and deadbands sent by Nav2 to the robot. 
	\item \textbf{Costmap} is a representation of the environment using a regular 2D grid of cells with a cost (unknown, free, occupied, or inflated) and is used for generate the global plan or to compute local control efforts.
\end{itemize}
The next things that allow to use Nav2 is a:
\begin{itemize}
	\item \textbf{state estimation} of the robot that generate a suitable TF tree, a tree structure of coordinate frames generated using the transform library\cite{6556373}, based on the \href{https://www.ros.org/reps/rep-0105.html}{REP 105}, that is should provide this structure: \texttt{map} $\rightarrow$ \texttt{odom} $\rightarrow$ \texttt{base\_link}. According to the REP 105 they are defines as:
	\begin{itemize}
		\item \texttt{map} : a world fix frame that is not continuos that is the pose of the robot can change in discrete jumps at any time. This is useful as a long-term global reference but not in the short-term.
		\item \texttt{odom} : a world fix frame that can drift over time to be continuous. This allow to be useful in an short-term local reference but not good for long-term one.
		\item \texttt{base\_link}: a robot fix frame.
	\end{itemize}
	The \texttt{odom} $\rightarrow$ \texttt{base\_link} link can be calculated using different sensors. To increase the performance of our estimation we will use the \texttt{robot\_localization} a node that provide nonlinear state estimation nodes using Kalman Filter \cite{MooreStouchKeneralizedEkf2014}.\\
	The \texttt{map} $\rightarrow$ \texttt{odom} link can be generate with a global positioning system like Simultaneous Localization And Mapping (SLAM) method or using the one provided by Nav2, Adaptive Monte-Carlo Localization (AMCL). 
	\item \textbf{map} that can be build during navigation using a SLAM tool or loaded. A powerful SLAM is Cartographer that will be described in the next section and it's the one used to build the map that we are going to use.
\end{itemize}
\subsection{Cartographer}
Cartographer\cite{45466} is a SLAM that work using two subsystem: a \textbf{Local SLAM} (called \textbf{Frontend}) that build a series of locally consistent \textbf{submaps} from successive scans and the pose extrapolator but with the possibility that can drift during acquisition and a \textbf{Global SLAM} (called \textbf{Backend}) that find loop closure constraints scan-matching scans against submaps using a global optimization in a way to obtain a consistent map. It can perform a 2-3 cm accuracy mapping but required a lot tuning of the parameters.

Currently these are some the fleet management system available:
\begin{itemize}
	\item \textbf{Isaac Mission Dispatch}\footnote{\href{https://github.com/NVIDIA-ISAAC/isaac_mission_dispatch}{https://github.com/NVIDIA-ISAAC/isaac\_mission\_dispatch}} is a NVIDIA microservice enble fleet managment software to submit missions to multiple robots and monitor the robot and mission status. 	\item \textbf{ROOSTER Fleet Management}\footnote{\href{https://github.com/ROOSTER-fleet-management}{https://github.com/ROOSTER-fleet-management}} is a ROS 1 based open source project to develop a heterogeneous fleet management solution with task allocation, scheduling and routing capabilities.

	\item \textbf{Transitive Robotics}\footnote{\href{https://transitiverobotics.com/}{https://transitiverobotics.com/}} is an open-source framework for full-stack robotics. \section{Open-RMF description}
Open-RMF is a flexible tool set build on ROS 2 for allowing the interaction between heterogeneous robot fleets. It uses a standardized protocol for communication with infrastructures, environments and automations to optimize the use of the critical resources (like other robots, lifts, doors, narrow passages) of a system to control the traffic. It gives intelligence to a system avoiding conflicts for the available resources and assigned it correctly.
This figure describe how works Open-RMF:
\begin{figure}[h]

	\includegraphics[width=0.8\linewidth]{img/RMF\_struct.png}
	\captionof{figure}{Open-RMF Structure}
\end{figure}
\\
There are 3 type of fleet adapter :
\begin{itemize}
	\item \textit{Full Control}: have full status updates and full control on the path
	\item \textit{Traffic Light}: have full status updates and a pause/resume control 
	\item \textit{Read Only}:  have only status updates. It can be only one of this type because more of them will make avoiding deadlock or resource conflict nearly impossible.
\end{itemize}
In case there is a fleet with \textit{No Interface} this can result deadlocks on the available resources and is not compatible with a RMF system.
\\
The Open-RMF core \texttt{rmf\_core} is built on this list of packages:
\begin{itemize}
	\item \texttt{rmf\_traffic}: Core scheduling and traffic management systems based on the following traffic deconfliction: \textit{Prevention} and \textit{Negotiation} using a living platform-agnostic Traffic Schedule Database.
	\begin{figure}[h]
		\centering
		\includegraphics[width=0.8\linewidth]{img/RMF_tut_schedule.png}
		\captionof{figure}{Open-RMF Schedule structure}
	\end{figure}
		\begin{itemize}
			\item \textit{Prevention} when there are some changes in the DB, like cancellations, the fleet manager can plan the routes to avoid conflicts. 
			\item \textit{Negotiation} When thought the Database there is an upcoming conflict between two or more schedule participants, it will send a conflict notice out to the relevant fleet managers, that will reply with their preferable path that can accommodate the others and through a external judge choose the best path to follow 
		\end{itemize}
	Conflict avoidance for automated guided vehicle AGV's is implemented with time-dependent extension to A* search for both path and task. This search takes time into account so that it can find paths through space and time that account for the motions of other agents that are in the traffic schedule.
	It's not designed for autonomous mobile robot (AMR) that is in development.
	\item \texttt{rmf\_traffic\_ros2}: provide the interface between rmf\_traffic and ros2
	\item \texttt{rmf\_task}: APIs and base classes for defining and managing Tasks in RMF.
	RMF supports three types of task requests out of the box:
	\begin{itemize}
		\item \textit{Clean}: For robots capable of cleaning floor spaces in facilities
		\item \textit{Delivery}: For robots capable of delivering items between locations in facilities
		\item \textit{Loop}: For robots capable to navigating back and forth between locations in facilities
	\end{itemize}
	\item \texttt{rmf\_dispatcher\_node}: RMF simplifies task allocation and management across multi-fleet systems. When a user submits a new task request, RMF will intelligently assign it to the robot in the fleet that can best perform the task as described in the image.

	\end{figure}
	\item \texttt{rmf\_battery}: rmf battery estimation 
	\item \texttt{rmf\_ros2}: ros2 adapters and nodes and python bindings for rmf\_core
	\item \texttt{rmf\_utils}: utility for rmf
	
\end{itemize}
