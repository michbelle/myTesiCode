\section{odometry estimation \texttt{odom} $\rightarrow$ \texttt{base\_link}}
As described before the odometry data given from the rover arent good and the navigation stack report big errors in rotation a well know fact of problem in estimation using skid-steering vehicles. For solve this problem we use the package \texttt{robot\_localization} in specific the Node \texttt{ekf\_node}.
This package allow fusing multiple sensor also of the same type, allow to publish in multiple message type like nav\_msgs/Odometry, allow to edit message from each sensor before insering in the estimation and is a continuous estimation that allow to estimate the position even if data is going to missing for a long period.
For launching the node there are provide the following launch file:\\
\hspace*{10mm}\texttt{1<r/s>\_robot\_localizationEKF.launch.py}
\subsection{odometry estimation configuration}
Has describe before and also in the doc\footnote{\href{https://docs.ros.org/en/noetic/api/robot_localization/html/index.html}{https://docs.ros.org/en/noetic/api/robot\_localization/html/index.html}} of the node for adding the sensors we added this rows at the configuration file \texttt{odom0:odometry/wheels} and \texttt{imu0:imu/data} that are the estimation described before. Also we need to choose which components of the state we want to fuse using this array and set \texttt{true} if we want it to fuse:\\
\texttt{sensorX\_config}:$ [X, Y, Z, roll, pitch, yaw, \dot{X}, \dot{Y}, \dot{Z}, \dot{roll}, \dot{pitch}, \dot{yaw}, \ddot{X}, \ddot{Y}, \ddot{Z}] $\\
for the IMU we used only the yaw velocity while for the odometry we select only the velocity along the x and y.\\
Then is also possible to tune the process noise covariance matrix $ Q $ and represents the noise we add to the total error after each prediction step.  In general, the larger the value for Q relative to the variance for a given variable in an input message, the faster the filter will converge to the value in the measurement.

In this part we will refer a lot on the porting documentation refered before \footnote{\href{https://docs.ros.org/en/rolling/How-To-Guides/Migrating-from-ROS1.html}{https://docs.ros.org/en/rolling/How-To-Guides/Migrating-from-ROS1.html}}\footnote{\href{https://industrial-training-master.readthedocs.io/en/melodic/\_source/session7/ROS1-to-ROS2-porting.html}{https://industrial-training-master.readthedocs.io/en/melodic/\_source/session7/ROS1-to-ROS2-porting.html}} and the documentection from Nav2 : "Writing a New Planner Plugin"\footnote{\href{https://docs.nav2.org/plugin_tutorials/docs/writing_new_nav2planner_plugin.html}{https://docs.nav2.org/plugin\_tutorials/docs/writing\_new\_nav2planner\_plugin.html}}

\subsubsection{Porting code to Nav 2}
\begin{itemize}
	\item in plugin definition: we move from thr base\_class\_type of nav\_core::BaseGlobalPlanner to nav2\_core::GlobalPlanner.
	\item because it is a plugin based on \texttt{nav2\_core::GlobalPlanner} it inherits 5 pure virtual methods (\texttt{configure()},\texttt{activate()},\texttt{deactivate()},\texttt{cleanup()},\texttt{createPlan()}) that required override and used to compute the trajectories. Now we describe each method
	\begin{itemize}
		\item \texttt{configure()} : called when node enters \texttt{on\_configure} state, used for perform declarations of ROS parameters and initialization of planner’s member variables. The input parameters are: shared pointer to parent node, planner name, tf buffer pointer and shared pointer to costmap. This replace the \texttt{initialize} method used in ROS 1 and also the class initialization. Also it's parametrs are used to link the planner information locally:
		\begin{itemize}
		\item \texttt{rclcpp\_lifecycle::LifecycleNode::WeakPtr} to link to the base class
		\item the name of the plugin
		\item a link to the \texttt{tf} with \texttt{std::shared\_ptr<tf2\_ros::Buffer>}
		\item the map with \texttt{std::shared\_ptr<nav2\_costmap\_2d::Costmap2DROS>}
		\end{itemize}
		\item \texttt{activate()} : called when node enters \texttt{on\_activate} state, used for implement operations which are necessary before planner goes to an active state.
		\item \texttt{deactivate()} : called when node enters \texttt{on\_deactivate} state, used for implement operations which are necessary before planner goes to an inactive state.
		\item \texttt{cleanup()} : called when node enters \texttt{on\_cleanup} state, should clean up resources which are created for the planner.
		\item \texttt{createPlan()} : called when planner server demands a global plan for specified start and goal pose. replace the makePlan used in ROS 1 and return a path as \texttt{nav\_msgs::msg::Path} using the start and end position as \texttt{geometry\_msgs::msg::PoseStamped}
	\end{itemize}
	\item at the end we placed the code that is used also or plugins:\\
\begin{listing} [ht!]
\begin{minted}{cpp} 
#include "pluginlib/class_list_macros.hpp"
PLUGINLIB_EXPORT_CLASS(<type of the plugin class>, <type of the base class>);
\end{minted}
\end{listing}
	\item because it's a plugin we need to add a plugin declaration where is package.xml is located and edit the CMake file as described in the doc for plugins\footnote{\href{https://docs.ros.org/en/jazzy/Tutorials/Beginner-Client-Libraries/Pluginlib.html}{https://docs.ros.org/en/jazzy/Tutorials/Beginner-Client-Libraries/Pluginlib.html}}.
\end{itemize}

\chapter{Integration of the navigation stack with Open-RMF}
For integrating a fleet to Open-RMF we need before set the rmf\_core that needs the information of the facility. this is possible using the \textbf{traffic editor tool}\footnote{\href{https://github.com/open-rmf/rmf\_traffic\_editor}{https://github.com/open-rmf/rmf\_traffic\_editor}}  \footnote{\href{https://osrf.github.io/ros2multirobotbook/intro.html}{https://osrf.github.io/ros2multirobotbook/intro.html}}. also it able to build is \textbf{route maps}, this maps are used to predict the navigation paths that the robots will took allowing RMF to avoid conflicts, this procedure is called "traffic management".
\section{traffic management - route maps generation}
We are using the traffic\_editor to create the map and relative routes.
We started with the map obtained from Cartographer and start a new project \texttt{*.building.yaml}. Then, there are some drawing of the facility's plans and also that was added. We then to design the traffic flow for the floor following the best practice to obtain a optimize plan \footnote{\href{https://osrf.github.io/ros2multirobotbook/integration\_nav-maps-strategies.html}{https://osrf.github.io/ros2multirobotbook/integration\_nav-maps-strategies.html}}, the traffic editor allow to define this following components to the map that is going to be used as route map:
\begin{itemize}
	\item \textbf{vertex}: they are waypoints or the definition of wall, door or else. The properties of a vertex can be:
	\begin{itemize}
		\item \texttt{is\_holding\_point} : the robot is allowed to wait at this waypoint for an indefinite period of time.
		\item \texttt{is\_parking\_spot}: robot is required to park itself.
		\item \texttt{is\_passthrough\_point}: waypoint which the robot shouldn't stop.
		\item \texttt{is\_charger}: charging station for a robot
		\item \texttt{is\_cleaning\_zone}: used for the \texttt{Clean} task, indicate if is a clean zone where to start the cleaning
		\item \texttt{dock\_name}: used when the robot is executing their custom docking sequence. \alert{send a command to rmf to dock the robot.}
		\item \texttt{pickup\_dispenser}: dispenser workcell for \texttt{Delivery} Task
		\item \texttt{dropoff\_ingestor}: ingestor workcell for \texttt{Delivery} Task
		\item \texttt{spawn\_robot\_type}: used in simulation to spawn a robot model 
		\item \texttt{spawn\_robot\_name}: used in simulation to identify a robot spawned
	\end{itemize}
	\item \texttt{measurement} allow to add a measurement to set the scale of the drawing. In our case we used the \alert{know} width of the hallway.
	\item \texttt{door}: used both for interacting with the real world than for simulation. if a robot is going to pass throught a lane where is a door, rmf will request to open the door.
	\item \texttt{traffic lane}: connect waypoints and are the paths for a fleet to follow, they are divided by groups and multiple fleet can be assign on a group. rmf suppose that are straight lines for control the vehicles. the lanes can be unidirectional or bidirectional and orientation if required the robot to navigate forward or backward.
	\item \texttt{fiducials}: used for align multiple floor and used as a link to ROS 2 map, are visible throught multiple floor and give an information about their position respect the map.
	\item \texttt{lift}: used for align multiple floor and used as a link to ROS 2 map, are visible throught multiple floor and give an information about their position respect the map.
	\item \texttt{walls}: for simulation add the walls to the world that will generate.
	\item \texttt{floor}: for simulation add the ground plane for robots wo walk on. can added hole for lifts.
	\item \texttt{environment assets}: for simulation add models of different furniture for gazebo. 
\end{itemize}
This plan take into account for planning this factor:
\begin{itemize}
	\item in the hallways can pass only one robot
	\item Holding points (leaf nodes) are added along the corridor or near the begin or the end of it for giving way to one another. If there are some task waypoint is suggested to add a very low limit speed to avoid to use them as holding points.
	\item \alert{mutex lanes or waypoints, At any point of time, only one robot is allowed to occupy any waypoint or lane belonging to the same mutex group, allow to avoids deadlocks.}
\end{itemize}

\subsection{Zenoh}
Zenoh\footnote{\href{https://zenoh.io/}{https://zenoh.io/}} is a pub/sub/query protocol unifying data in motion, data at rest and computations. It blends traditional pub/sub with geo distributed storage, queries and computations, while retaining a well level of time and space efficiency. It allow to send only specific topic through the web reducing bandwidth to a specific server.
On this server is need to launch a Zenoh router with (\texttt{\$ zenohd}), but there can be multiple instance of Zenoh router for redundancy. Then as described in the repo is suggested to use the binaries of \texttt{zenoh-bridge-ros2dds} one on the server and one on each robot with a configuration file. On the server it's configurated to accept all the traffic \alert{test se necessario avere avere il server} from each machine can reach it, while on the client we need to setup:
\begin{itemize}
 \item the \texttt{namespace} as the one associated to the file of configuration of the fleet
 \item allow to publish the frame status of the robot (\texttt{.*/tf} and \texttt{.*/tf\_static}) and if we could also the battery information (\texttt{.*/battery\_state}) and allow also the action servers that control the navigation(\texttt{.*/navigate\_to\_pose})
 \item setup zenoh configuration defining the mode and the address of the server, with is protocol and its port that th client will \texttt{connect} and \texttt{listen} to (\texttt{tcp/<ip address server>:7447})
\end{itemize}

\\
\alert{The RMF commands from waypoint to waypoint: RMF commands the robot from waypoint to waypoint, and it leaves the low level navigation to each robot's navigation stack. So if the robot chooses to use a non-straight route, it means that the RMF navigation graph might need to be re-drawn or reconsidered (if there are constant obstacles around), or the navigation stack of the robot should be tuned to allow tighter tolerances for static/dynamic obstacles. but how the robot chooses to navigate between them is out of RMF's control, since RMF does not have dynamic obstacle information, or if there are new static obstacles, it needs to be reflected into RMF's traffic navigation graph}
