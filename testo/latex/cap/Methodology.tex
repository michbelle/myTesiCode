\section{Odometry Estimation \texttt{odom} $\rightarrow$ \texttt{base\_link}}
As previously discussed, the raw odometry data provided by the rover are not sufficiently accurate, particularly in rotational movements\cite{MooreStouchKeneralizedEkf2014}. This is a well-known issue in odometry estimation for skid-steering vehicles, which tend to produce significant drift and errors during turns.\\
To address this problem, we used the \texttt{robot\_localization} package\cite{MooreStouchKeneralizedEkf2014}, specifically the \texttt{ekf\_node}.
This package enables the fusion of multiple sensor, even multiple instances of the same sensor type, and supports output in various ROS message formats, such as \texttt{nav\_msgs/Odometry}. It also allows preprocessing of sensor messages prior to inserting into the estimation process. The filter performs continuous state estimation and is robust to intermittent sensor data loss, maintaining a coherent position estimate over time.\\
To launch the EKF node, the following launch file was wrote:\\
\hspace*{10mm}\texttt{1<r/s>\_robot\_localizationEKF.launch.py}

\subsection{Configuration Odometry Estimation in \texttt{ekf\_node}}
As described previously and in the documentation of the node\footnote{\href{https://docs.ros.org/en/noetic/api/robot_localization/html/index.html}{https://docs.ros.org/en/noetic/api/robot\_localization/html/index.html}}, we added the information about the sensors used to the configuration file. The principal information to include is the type of sensor and on which topic subscribe for the data, \texttt{odom0:odometry/wheels} and \texttt{imu0:imu/data}, and, for each sensor, we need to choose which components of the state measurement data we want to fuse using the following array, setting the corresponding values to \texttt{true} for those we wish to include and \texttt{false} for those we do not:\\
\texttt{sensorX\_config}:$ [X, Y, Z, roll, pitch, yaw, \dot{X}, \dot{Y}, \dot{Z}, \dot{roll}, \dot{pitch}, \dot{yaw}, \ddot{X}, \ddot{Y}, \ddot{Z}] $\\
\alert{ In our case we used only the yaw velocity for the IMU while for the odometry we select only the velocity along the x and y}.\\
It is also possible to tune the process noise covariance matrix $ Q $, which represents the noise we add to the total error after each prediction step. Generally, the larger the value of $ Q $ relative to the variance of a given variable in an input message, the faster the filter will converge to the value indicated by the measurement.

\subsection{Porting ROS 1 DStarGlobalPlanner to ROS 2}
As mentioned previously, the \texttt{DStarGlobalPlanner}\footnote{\href{https://github.com/ElettraSciComp/DStar-Trajectory-Planner/tree/ros2_port}{https://github.com/ElettraSciComp/DStar-Trajectory-Planner/tree/ros2\_port}} is a implementation of the D* informed incremental search algoritm with external optimizers\cite{10.1007/978-3-031-67295-8_33} for the ROS 1 \texttt{move\_base} package\footnote{\href{https://wiki.ros.org/move_base}{https://wiki.ros.org/move\_base}}.\\
Since the code is written using ROS 1, it needs to be ported to ROS 2. The procedure involved splitting the process into two parts. In the first part we ported the base structure from ROS 1 to ROS 2 using the porting documentation \footnote{\href{https://docs.ros.org/en/rolling/How-To-Guides/Migrating-from-ROS1.html}{https://docs.ros.org/en/rolling/How-To-Guides/Migrating-from-ROS1.html}}\footnote{\href{https://industrial-training-master.readthedocs.io/en/melodic/\_source/session7/ROS1-to-ROS2-porting.html}{https://industrial-training-master.readthedocs.io/en/melodic/\_source/session7/ROS1-to-ROS2-porting.html}} and in the second part, we adjust the code to fit the structure of a planner plugin using the documentation from Nav2 : "Writing a New Planner Plugin"\footnote{\href{https://docs.nav2.org/plugin_tutorials/docs/writing_new_nav2planner_plugin.html}{https://docs.nav2.org/plugin\_tutorials/docs/writing\_new\_nav2planner\_plugin.html}}.
Is now described the 2 phases of porting the code, the first one is the Nav2 structure porting procedure and the second part adapt the old code to ROS 2.
\subsubsection{Porting code from ROS 1 to ROS 2}
In the \texttt{package.xml} file, which describe the package as an organizational unit for your ROS 2 code, the following changes were made:
\begin{itemize}
	\item \texttt{buildtool\_depend} : \texttt{catking} $\rightarrow$ \texttt{ament\_cmake}: \texttt{ament\_cmake} is the new build system for CMake based packages. Many utilities for managing packages have been added compared to \texttt{catking} and more information is available in the documentation\footnote{\href{https://docs.ros.org/en/rolling/Concepts/Advanced/About-Build-System.html}{https://docs.ros.org/en/rolling/Concepts/Advanced/About-Build-System.html}}.
	\item \texttt{roscpp} $\rightarrow$ \texttt{rclcpp}: \texttt{rclcpp} is the new ROS client library for C++, built on \texttt{rcl}, which support the implementation of language specific ROS Client Libraries. The \texttt{rcl} communicates with \texttt{rmw}, the interface of middleware primitives that are used by the higher level ROS API's and handle the communication with the \texttt{DDS}.
	\item update the naming of all the packages.
	\item to inform \texttt{colcon} that the package uses \texttt{ament\_cmake}, it is necessary to specify this in the \texttt{build\_type}.
\end{itemize}
After that we edited the \texttt{CMakeLists.txt} and the major changes are:
\begin{itemize}
	\item update the naming of all the packages.
	\item set the new standard of C++ to 17.
	\item \texttt{find\_package()} required to be called for each package
	\item call \texttt{ament\_export\_dependencies()} to indicates which \texttt{ament} packages are necessary at runtime.
	\item declare the package in ROS using \texttt{ament\_package()} at the end.
\end{itemize}
Other minor changes are:

\begin{itemize}
	\item Log calls are changed from \texttt{ROS\_} to \texttt{RCLCPP\_}
	\item Structure of some messages are changed (es. \texttt{geometry\_msgs::PoseStamped} $\rightarrow$ \texttt{geometry\_msgs::msg::PoseStamped}).
	\item The structure of the C++ program now required the use of smart pointer.
\end{itemize}

Other changes relate to ROS 2 are described in the next section because they are relate to Nav2.

\subsubsection{Porting code from ROS 1 Navigation stack to Nav2}
This is a list of the changes made for porting the planner to Nav2:
\begin{itemize}
	\item Since it is a global planner, it inherits from new abstract interface for global planners, \texttt{nav2\_core::GlobalPlanner}. As a result, we updated the\\ \texttt{global\_planner\_plugin.xml} file changing the \texttt{base\_class\_type}.
	\item Because it is a plugin based on \texttt{nav2\_core::GlobalPlanner}, it inherits 5 pure virtual methods that are necessary for correct operation: \texttt{configure()}, \texttt{activate()}, \texttt{deactivate()} and \texttt{cleanup()}, \texttt{createPlan()}. We will now describe each method:
	\begin{itemize}
		\item \texttt{configure()}: it's called when the node enters \texttt{on\_configure} state, is used for perform declarations of ROS parameters and initialization of planner’s member variables. The input parameters are:
		\begin{itemize}
			\item \texttt{rclcpp\_lifecycle::LifecycleNode::WeakPtr} A weak pointer to link to the base class.
			\item The name of the planner.
			\item A share pointer to the \texttt{tf} buffer\\ \texttt{std::shared\_ptr<tf2\_ros::Buffer>}.
			\item A shared pointer to the costmap\\ \texttt{std::shared\_ptr<nav2\_costmap\_2d::Costmap2DROS>}.
			\item For jazzy also: \texttt{std::function<bool()> cancel\_checker} that allow for the cancellation of the current planning task.
		\end{itemize}
		This replace the \texttt{initialize} method and the class initialization in ROS 1. 
		\item \texttt{activate()}: Called when the node enters \texttt{on\_activate} state, used for implement operations which are necessary before planner goes to an active state. In our case we allocate memory and fill our internal costmap \texttt{state\_map}, which is used by the D* (\texttt{dstar}) algorithm.
		\item \texttt{deactivate()}: Called when the node enters \texttt{on\_deactivate} state, used for implement operations which are necessary before planner goes to an inactive state. In our case, this method is not used and is left empty.
		\item \texttt{cleanup()} : Called when the node enters \texttt{on\_cleanup} state, used for clean up resources which are created for the planner. In our case we destroys the allocated memory used by \texttt{state\_map} and \texttt{dstar}. 
		\item \texttt{createPlan()}: Called when planner server demands a global plan from a start and goal pose. It required the start and goal position as\\ \texttt{geometry\_msgs::msg::PoseStamped} and return and return a path \texttt{nav\_msgs::msg::Path}. Replace the \texttt{makePlan} used in ROS 1.
	\end{itemize}
	\item At the end of the C++ code we write this two rows that are used to export the planner:\\
\begin{listing} [ht!]
\begin{minted}{cpp} 
#include "pluginlib/class_list_macros.hpp"
PLUGINLIB_EXPORT_CLASS(<type of the plugin class>, <type of the base class>);
\end{minted}
\end{listing}
	\item Because it's a plugin, we need to add a plugin declaration creating a file \texttt{global\_planner\_plugin.xml}, where is located the \texttt{package.xml}, that describe the plugin and edit the CMake file as described in the documentation for plugins\footnote{\href{https://docs.ros.org/en/rolling/Tutorials/Beginner-Client-Libraries/Pluginlib.html}{https://docs.ros.org/en/rolling/Tutorials/Beginner-Client-Libraries/Pluginlib.html}}.
\end{itemize}

\chapter{Integration of the navigation stack with Open-RMF}
To integrate a fleet in Open-RMF, we first need information about the structure af a building, like automatic doors or lifts that can be controlled, and the \textbf{route maps} that robots can use. The \textbf{route maps} are used to predict the navigation paths that the robots will took allowing RMF to avoid conflicts, this procedure is called "traffic management". All these information have to be stored in a file that can be generated using the \textbf{traffic editor tool}\footnote{\href{https://github.com/open-rmf/rmf\_traffic\_editor}{https://github.com/open-rmf/rmf\_traffic\_editor}}  \footnote{\href{https://osrf.github.io/ros2multirobotbook/intro.html}{https://osrf.github.io/ros2multirobotbook/intro.html}}, a tool provided by Open-RMF. It now follow a description of how it works and how we had used it.
\section{Traffic Management - Route Maps Generation}
We start a new project \texttt{*.building.yaml} and then add the map generated by Cartographer and the drawing of the facility's plans. We then defined the position of important point in the map and design the traffic flow for the floor following the best practice as describe here\footnote{\href{https://osrf.github.io/ros2multirobotbook/integration\_nav-maps-strategies.html}{https://osrf.github.io/ros2multirobotbook/integration\_nav-maps-strategies.html}}. Now we use the following components of the traffic editor to insert all the information:
\begin{itemize}
	\item \textbf{vertex}: They are waypoints or the definition of wall, door or else. The properties of a vertex can be:
	\begin{itemize}
		\item \texttt{is\_holding\_point} : the robot is allowed to wait at this waypoint for an indefinite period of time.
		\item \texttt{is\_parking\_spot}: robot is required to park itself.
		\item \texttt{is\_passthrough\_point}: waypoint which the robot shouldn't stop.
		\item \texttt{is\_charger}: charging station for a robot.
		\item \texttt{is\_cleaning\_zone}: used for the \texttt{Clean} task, indicate if is a clean zone that is where to start the cleaning.
		\item \texttt{dock\_name}: used when the robot is executing their custom docking sequence. \alert{send a command to rmf to dock the robot}.
		\item \texttt{pickup\_dispenser}: dispenser workcell for \texttt{Delivery} Task.
		\item \texttt{dropoff\_ingestor}: ingestor workcell for \texttt{Delivery} Task.
		\item \texttt{spawn\_robot\_type}: used in simulation to spawn a robot model.
		\item \texttt{spawn\_robot\_name}: used in simulation to identify a robot spawned.
	\end{itemize}
	\item \texttt{measurement} allow to add a measurement to set the scale of the drawing. In our case we used the \alert{know} width of the hallway.
	\item \texttt{door}: is used both for interacting with the real world than for simulation. If a robot is going to pass through a lane where is a door, RMF will request to open the door and also will add the model to the simulation.
	\item \texttt{traffic lane}: connect waypoints and are the paths for a fleet to follow, they are divided by groups and multiple fleet can be assign on a group. RMF suppose that are straight lines for planning. The lanes can be unidirectional or bidirectional and have a specific "orientation" if required the robot to navigate forward or backward.
	\item \texttt{fiducials}: used for align multiple floor and used as a link to ROS 2 map, are visible through multiple floor and give an information about their position respect the map.
	\item \texttt{lift}: used for align multiple floor and used as a link to ROS 2 map, are visible through multiple floor and give an information about their position respect the map.
	\item \texttt{walls}: used in simulation, add the walls to the world that will generate.
	\item \texttt{floor}: used in simulation, add the ground plane for robots to walk on. It can be edited to add holes for the lifts.
	\item \texttt{environment assets}: used in simulation, add Gazebo models of different furniture. 
\end{itemize}
These decision were taken place when planning for the route maps:
\begin{itemize}
	\item In the hallways can pass only one robot.
	\item Holding points (leaf nodes) are added along the corridor or near the begin or the end of it for giving way to one another. For some task waypoint is suggested to add a very low limit speed to avoid that RMF will use them as holding points.
	\item Adding mutex lanes or waypoints that allow, at any point of time, only one robot to occupy any waypoint or lane belonging to the same mutex group. This allows to avoids deadlocks.
\end{itemize}

\subsection{Setup fleet}
For using the Free fleet we need to create the configuration file of the fleet. It a file that describe the robots of a fleet that have the same characteristics. These are the necessary information: name of the fleet, limits in velocity, their size and some mechanical info, some info their power management, what task they are capable of and a list of all robot that are inside this fleet with their name, what charger they use and the correlation in position between the map on the robot and the one used in RMF.\\
Setup the fleet, we need to setup Zenoh.
\subsection{Setup Zenoh}
Zenoh\footnote{\href{https://zenoh.io/}{https://zenoh.io/}} is a pub/sub/query protocol unifying data in motion, data at rest and computations. It blends traditional pub/sub with geo distributed storage, queries and computations, while retaining a well level of time and space efficiency. It allow to send only specific topic through the web reducing bandwidth to a specific server.\\
To setup this part of using Zenoh we need to:
On a server is needed a Zenoh router that can be launched with (\texttt{\$ zenohd}), but there can be multiple instance of Zenoh router for redundancy.\\
Then, as described in the documentation, on each robot and the server on witch run RMF there is the need to launch the standalone executable \texttt{zenoh-bridge-ros2dds} that bridges all ROS 2 communications using DDS over Zenoh. The configuration of this file depend on the machine. On the server it's configured to accept all the traffic \alert{test se necessario avere il server} from each robot, while on the robot we need to setup:
\begin{itemize}
 \item the \texttt{namespace} that is the same one associated to the file of configuration of the fleet
 \item enabling to publish the frame status of the robot (\texttt{.*/tf} and \texttt{.*/tf\_static}) and the battery information (\texttt{.*/battery\_state}) \item enabling the communication from the action servers that control the navigation(\texttt{.*/navigate\_to\_pose})
 \item setup Zenoh specific configurations that define the mode of communication and the server's address, with its protocol and port that the client will \texttt{connect} and \texttt{listen} to (\texttt{tcp/<ip address server>:7447})
\end{itemize}
